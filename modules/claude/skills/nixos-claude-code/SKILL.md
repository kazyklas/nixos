# Managing Claude Code from this NixOS config

Everything Claude Code reads out of `~/.claude` is generated by home-manager's
`programs.claude-code` module, configured in `modules/claude-code.nix` with
content living under `modules/claude/`. Nothing in `~/.claude` that the module
owns should ever be edited directly: it is a read-only symlink into
`/nix/store`, and the next rebuild would discard the edit anyway.

## Where things live

```
modules/claude-code.nix          the module invocation (options go here)
modules/claude/
├── skills/<name>/SKILL.md       one directory per skill, auto-discovered
├── agents/<name>.md             (create when first needed)
├── commands/<name>.md           (create when first needed)
└── hooks/<name>                 (create when first needed)
```

`skills` is wired as a **path** (`skills = ./claude/skills;`), which means
home-manager `readDir`s the directory. Adding a skill is "make a folder with a
`SKILL.md` in it" — no edit to `modules/claude-code.nix` required.

## The three-step loop for any change

1. Add or edit the content under `modules/claude/`.
2. **`git add` the new files.** This flake only evaluates git-tracked files, so
   an untracked skill directory is invisible both to `readDir` and to the
   build. This is the single most common reason a new skill "doesn't show up".
3. `sudo nixos-rebuild switch --flake /home/tklas/nixos#nixos`, then restart the
   Claude Code session so it re-reads the config directory.

Verify with `/skills` (or `/agents`, `/help` for commands) in a fresh session,
or by checking the symlink resolves: `ls -l ~/.claude/skills/`.

## Option → path reference

Every option below lives under `programs.claude-code`. `configDir` defaults to
`~/.claude`; if it is ever changed, the module exports `CLAUDE_CONFIG_DIR`
automatically.

| Option | Produces | Notes |
| --- | --- | --- |
| `skills = ./claude/skills;` | `skills/` (recursive) | Path form; auto-discovers one folder per skill. Mutually exclusive with the attrset form. |
| `skills.<name>` | `skills/<name>/` or `skills/<name>/SKILL.md` | Attrset form. Directory path → recursive copy; file path or inline string → `SKILL.md`. |
| `agents.<name>` | `agents/<name>.md` | `.md` is appended for you — name it `code-reviewer`, not `code-reviewer.md`. |
| `commands.<name>` | `commands/<name>.md` | Becomes the slash command `/<name>`. `.md` appended. |
| `hooks.<name>` | `hooks/<name>`, mode +x | **No extension appended.** Include it yourself (`pre-edit.sh`). |
| `rules.<name>` | `rules/<name>.md` | Every markdown file in `rules/` is auto-loaded as memory. |
| `outputStyles.<name>` | `output-styles/<name>.md` | |
| `context` | `CLAUDE.md` | Inline string, or a path to a file. |
| `settings` | `settings.json` | See the warning below. |
| `mcpServers`, `lspServers` | a synthesized plugin named `hm` | Namespaces tools as `mcp__plugin_hm_<server>__<tool>`. |
| `plugins.<name>` | a personal plugin directory | Prefer the attrset form; the list form derives unstable names from store paths. |
| `marketplaces.<name>` | `plugins/known_marketplaces.json` + a `settings.json` entry | Setting this takes over `settings.json`. |
| `agentsDir`, `commandsDir`, `hooksDir`, `rulesDir` | the whole directory, recursively | The directory equivalents of the attrset options above. |

All content options accept either an inline string or a path. Prefer a path for
anything longer than a few lines: it keeps the Nix file readable and the content
gets syntax highlighting and a sane diff.

## Adding each kind of thing

**A skill.** Create `modules/claude/skills/<name>/SKILL.md` with `name` and
`description` frontmatter. Optional `scripts/`, `references/` and `assets/`
subdirectories come along automatically — the link is recursive. Use the
`skill-creator` skill for the authoring methodology itself.

**A slash command.** Add to `modules/claude-code.nix`:

```nix
commands.commit = ./claude/commands/commit.md;   # -> /commit
```

**A subagent.** Same shape, under `agents`. The markdown file needs its own
`name`/`description`/`tools` frontmatter — the module does not synthesize it.

**Global context.** `context = ./claude/CLAUDE.md;` writes `~/.claude/CLAUDE.md`.
For anything modular, prefer `rules` — files there load as memory too, and
splitting them keeps diffs small.

**A hook.** This takes two halves, and they are easy to confuse:

- `hooks.<name>` installs an *executable script* into `~/.claude/hooks/`.
- `settings.hooks` is the *wiring* that tells Claude Code when to run it
  (`PreToolUse`, `PostToolUse`, matchers, …).

A script with no wiring never fires. Wiring requires setting `settings`, so
read the warning first.

```nix
hooks."format.sh" = ./claude/hooks/format.sh;
settings.hooks.PostToolUse = [{
  matcher = "Edit|Write";
  hooks = [{ type = "command"; command = "${config.home.homeDirectory}/.claude/hooks/format.sh"; }];
}];
```

## Warning: `settings` makes settings.json read-only

The module only manages `~/.claude/settings.json` if `settings` or
`marketplaces` is non-empty. Right now both are empty on purpose, so that file
stays mutable and Claude Code can keep writing to it (`/config`, theme changes,
remembered permission grants, `/model`).

The moment either option is set, `settings.json` becomes a read-only store
symlink. Claude Code can no longer persist anything to it, and every setting
has to move into Nix. That is a legitimate choice, but it is a one-way door for
interactive settings — confirm the user wants it before setting either option,
and if they do, migrate the current contents of `~/.claude/settings.json` into
`settings` in the same change so nothing is silently lost.

## Other things worth knowing

- **Don't add `claude-code` to `home.packages`.** The module installs
  `programs.claude-code.package` itself (default `pkgs.claude-code`). Pin a
  different version there, or set `package = null` to manage the CLI elsewhere.
- **Skill and plugin names must not collide.** The module asserts this at eval
  time; the error names the duplicate directory.
- **Editing a skill requires a rebuild.** That is the cost of store symlinks and
  the reason they are reproducible. `mkOutOfStoreSymlink` would trade that away
  for live editing — `modules/noctalia-claude-chat.nix` does exactly that, but
  only because Noctalia hot-reloads `.luau` files and genuinely cannot work
  through an immutable path. Claude Code only reads these files, and re-reads
  them at session start, so the escape hatch isn't warranted here.
- **MCP and plugin options need a recent CLI.** Managed MCP/LSP/plugins require
  claude-code ≥ 2.1.76, and personal plugins ≥ 2.1.157. Below that the module
  falls back to a `--plugin-dir` wrapper that strict subcommands may reject.
- **The upstream module is readable.** When an option's exact behaviour matters,
  read the source rather than guessing:
  `nix flake prefetch --json github:nix-community/home-manager/$(jq -r '.nodes["home-manager"].locked.rev' flake.lock) | jq -r .storePath`
  then look at `modules/programs/claude-code/{options,lib,default}.nix`.
  `lib.nix` is where the filename conventions in the table above are decided.
